**第四章：计算架构与调度（Compute Architecture and Scheduling）**主要介绍了现代 GPU 的计算架构核心概念，以及这些硬件机制如何影响 CUDA 程序的执行性能。以下是该章核心内容的系统总结：

### 1. GPU 硬件架构（Architecture of a Modern GPU）
GPU 在硬件上被组织为高度线程化的**流式多处理器（Streaming Multiprocessors, SMs）**阵列。
* 每个 SM 内部包含多个**流式处理器（Streaming Processors）或称为 CUDA 核心（Cores）**，它们共享控制逻辑和片上内存资源。以 Ampere A100 GPU 为例，它拥有 108 个 SM，每个 SM 包含 64 个核心，整块芯片共计 6912 个核心。
* 除片上内存外，GPU 还配备了数吉字节（GB）的高带宽片外设备内存（即**全局内存 Global Memory**，在现代 GPU 中通常采用 HBM 或 HBM2 存储技术）。

### 2. 线程块调度（Block Scheduling）
当启动内核（Kernel）时，CUDA 运行时系统会发布一个由线程组成的网格（Grid）。
* 这些线程是以**线程块（Block）**为单位分配给 SM 的，即**同一个线程块中的所有线程必定会被同时分配到同一个 SM 上执行**。
* 硬件资源允许的情况下，一个 SM 可以同时容纳并运行多个线程块。
* 这种分配机制保证了同一个线程块内的线程能够在同一个 SM 上同时调度，从而使它们能够进行**屏障同步（Barrier Synchronization）**，并能够共享位于 SM 内部的高速、低延迟**共享内存（Shared Memory）**。

### 3. 同步与透明可扩展性（Synchronization and Transparent Scalability）
CUDA 允许同一个线程块内的线程使用 `__syncthreads()` 函数进行同步。
* **屏障同步**：当线程调用 `__syncthreads()` 时，它会暂停执行，直到该线程块中的所有其他线程都到达此同步点，从而确保不同阶段的计算能够正确衔接。如果不正确地在分支语句（如仅有部分线程进入的条件分支）中使用 `__syncthreads()`，可能会导致死锁。
* **透明可扩展性（Transparent Scalability）**：由于**不同线程块之间无法进行屏障同步**，CUDA 运行时系统可以以任意顺序调度和执行这些线程块，各线程块之间完全独立。这使得同一段 CUDA 代码可以无缝运行在不同规格的硬件上：低端 GPU 每次并行运行较少的线程块，而高端 GPU 则可以并行运行成百上千个线程块，实现性能的自动缩放而无需修改代码。

### 4. 线程束与 SIMD 硬件（Warps and SIMD Hardware）
在 GPU 硬件实现中，一旦线程块被分配到 SM，它会被进一步划分为以 **32 个线程**为单位的执行单元，称为**线程束（Warp）**。
* **线程束划分**：划分是基于 `threadIdx` 的线性连续索引进行的。对于多维线程块（如 2D 或 3D 块），系统会先按照行优先（Row-Major）的顺序将其线性化，然后再划分为线程束。如果线程块的大小不是 32 的倍数，最后一个线程束会用非活动（Inactive）线程填充凑满 32 个位置。
* **SIMD（单指令多数据）执行**：SM 采用 **SIMD 硬件模型**来执行同一个线程束中的所有线程。在任意时刻，控制单元会获取一条指令并将其分发给该线程束内的所有 32 个线程同时执行，每个线程将相同的指令应用到不同的数据上，这也常被称为单指令多线程（SIMT）。

### 5. 控制发散（Control Divergence）
当一个线程束内的线程在执行过程中走向不同的分支路径（例如 `if-else` 或循环次数不同）时，就会发生**控制发散**。
* **多遍执行机制**：因为 SIMD 硬件要求线程束内的所有线程在同一时刻只能执行同一条指令，当发散发生时，硬件必须分多遍（Passes）执行这些分支。例如在 `if-else` 结构中，硬件先执行满足 `if` 条件的线程（此时不满足的线程被屏蔽呈非活动状态），然后再执行满足 `else` 的线程，最后在分支结束后重新汇合执行。
* **Volta 及之后架构**：在 Pascal 及更早的架构中，发散的分支是严格串行执行的；而从 Volta 架构开始，引入了**独立线程调度（Independent Thread Scheduling）**，允许发散的分支并发或交错执行。
* **性能影响**：控制发散会降低核心的利用率，消耗额外的指令周期。最常见的控制发散发生于处理**边界条件**时（例如向量加法中的 `if (i < n)`）。然而，随着处理的数据集规模变大，边界判定导致发散的线程束占整体的比例会降得极低，此时控制发散对整体执行性能的影响可以忽略不计（通常小于 1%）。

### 6. 线程束调度与延迟容减（Warp Scheduling and Latency Tolerance）
为了最大化计算吞吐量，GPU 采用了**过度订阅（Oversubscription）**线程的设计。
* **延迟容减（Latency Tolerance / Hiding）**：当当前执行的线程束因为遇到长延迟操作（如片外全局内存访问、算术流水线延迟或分支指令）而需要等待时，SM 的硬件**线程束调度器（Warp Scheduler）**会立刻将其挂起，并选择另一个已经就绪（不等待任何结果）的线程束来执行。
* **零开销线程切换（Zero-overhead Thread Scheduling）**：与 CPU 需要将寄存器状态保存到内存中进行复杂的上下文切换不同，GPU 的 SM 在硬件寄存器堆（Register File）中直接保存了所有常驻线程束的运行状态，因此切换执行的线程束是瞬间完成的，没有任何额外时钟周期消耗。

### 7. 资源划分与占用率（Resource Partitioning and Occupancy）
SM 内部的执行资源（包括**寄存器、共享内存、线程块槽 Blocks Slots 和线程槽 Thread Slots**）是**动态划分**给所有常驻线程使用的。
* **占用率（Occupancy）**：定义为 SM 上实际驻留的线程束数量与该 SM 硬件支持的最大线程束数量的比值。占用率越高，GPU 隐藏延迟的能力通常越强。
* **性能断崖（Performance Cliff）**：因为资源是有限且动态分配的，如果一个内核使用的寄存器数量或共享内存略微增加，可能会导致 SM 上能够容纳的并发线程块数量突然减少，从而使占用率和性能出现剧烈下降。

### 8. 设备属性查询（Querying Device Properties）
为了让 CUDA 应用程序能够在不同规格的硬件上高效、健壮地运行，CUDA 提供了 **`cudaGetDeviceProperties()`** API 接口。
* 程序员可以通过此函数获取一个 `cudaDeviceProp` 类型的结构体，从而查询当前 GPU 设备的各项硬件参数，如流式多处理器数量（`multiProcessorCount`）、每个线程块的最大线程数（`maxThreadsPerBlock`）、每个 SM 的寄存器总量（`regsPerBlock`）以及硬件线程束大小（`warpSize`）等。
