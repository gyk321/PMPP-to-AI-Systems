# 基于 CUDA 的 Transformer 算子加速：先治"搬运"，再谈"算力"

## 一、前言：你可能一直优化错了东西

一听到"CUDA 算子加速"，大多数人的条件反射是：把 Python 循环搬进 kernel，用上 Tensor Core，把 FLOPS 打满。一个很流行的刷题式认知是——GPU 加速就是让芯片算得更快。

但这里有一个反直觉的事实：在 Transformer 最贵的几个算子上，GPU 的算力大部分时间在睡觉，真正的瓶颈是内存带宽。

拿 A100 算一笔账：FP16 Tensor Core 峰值 312 TFLOPS，HBM 带宽 2.0 TB/s，两者相除是 156 FLOP/byte。意思是：每从中央仓库搬 1 个字节进车间，理论上要顺手干 156 次浮点运算才不亏。H100 更夸张：989 TFLOPS 对 3.35 TB/s，比例涨到 295 FLOP/byte。而注意力里那些 N×N 的中间矩阵，恰恰是"搬得多、算得少"的重灾区。

所以本文想先纠正一个认知：CUDA 优化 Transformer 的主战场不是算力，是搬运。请把 GPU 想成一座工厂——车间里的工人手很快，但原料都堆在远处的中央仓库，产能由物流决定，不由手速决定。后面所有内容，都围绕这座工厂的仓库调度学展开。

## 二、问题唤醒：为什么通用框架不够快

Transformer 一次前向由几十个小算子接力完成：LayerNorm → QKV 投影（三个 GEMM）→ RoPE → attention → MLP（两个 GEMM）→ ……

在 PyTorch 的 eager 模式里，每个算子是一个独立 kernel。每个 kernel 干完活，把结果整个写回中央仓库；下一个 kernel 开工，再整个搬回来。一次前向，激活值在中央仓库和车间之间来回空转好几趟，而且中间没人记账——上家多搬的那一趟，下家根本不知道。

解码阶段更残酷：每生成一个 token，7B 模型的 14GB（fp16）权重都要从中央仓库过一次。哪怕一字节都不浪费，A100 上单个 token 至少也要 14GB ÷ 2TB/s ≈ 7ms，天花板约 143 token/s。这不是算力问题，这是仓库的物流问题。

通用框架看不见跨算子的冗余，所以我们必须下探到算子内部，甚至算子之间，重新安排仓库的搬运路线。那么前人是怎么安排的呢？

## 三、旧方案：能 GEMM 化的都 GEMM 化

前辈们的思路很朴素：把重活交给 cuBLAS。QKV 投影和 MLP 都是大矩阵乘，Tensor Core 这辆重型叉车一次能搬 16×16×16 的货箱，GEMM 能跑到算力峰值的 80%–90%。

标准 attention 也被"GEMM 化"：S = QKᵀ 交给 cuBLAS，把 N×N 的分数矩阵 S 整个写回中央仓库；然后 softmax 把 S 扫三遍（求 max 一遍、求 exp 和一遍、归一化一遍）；最后 O = P·V 再交给 cuBLAS。

这套方案看似无懈可击：每一个单算子都挺快。问题恰恰藏在那句"把 S 整个写回中央仓库"里。

## 四、旧方案的缺陷：中间货堆把仓库堵死了

S 的大小是 N×N。N=8192、fp16 时，一个头就是 134MB；一个 40 头的模型，一层就是 5GB 以上的中间货堆——比不少小模型本身还大。

更糟的是搬运次数：S 写回仓库 1 次，softmax 三趟读 3 次，P 写 1 次，P·V 再读 1 次，光 S/P 就进出仓库 6 次。N=8192 时一个头约 800MB 的流量里，真正有用的 Q、K、V 只有 6MB——98% 以上的搬运都在给中间货堆当苦力。

换一个角度同样能看清：注意力里的矩阵乘，计算强度只有约 d（d=128 时约 128 FLOP/byte），低于 A100 的 156 这条盈亏平衡线。它天生站在带宽那一侧，cuBLAS 算得再快，也得坐在车间里等仓库发货。

于是问题变成：能不能让 S 根本不进中央仓库，在车间里就地加工、用完即弃？这就是分块 + 在线 softmax 的起点。

## 五、核心原理：把中间货品留在车间

先认识这座工厂的三级物流体系：

- **工人口袋（寄存器）**：每个车间 256KB，一趟 1 个周期。它是毫米刻度，量手边的活。
- **车间工作台（共享内存）**：每个车间约 164–228KB，一趟二三十个周期。它是厘米和米刻度，量车间里的活。
- **中央仓库（HBM）**：几十 GB，带宽 2–3.35TB/s，一趟几百个周期。它是公里刻度，量整个模型。

FlashAttention 的做法可以浓缩成一句话：**分批搬货，就地加工，用完即弃。**

具体拆开看：

1. 外层循环按行把 Q 切成货箱；内层循环每次只把 K、V 的一个小块（比如 128×128）搬上工作台。
2. 在工作台上算这一小块的 S = QKᵀ。
3. 当场对这块做 softmax，并立刻乘上对应的 V 块，累进 O。O 的累加值一直放在工人口袋里。
4. 这一小块的 S/P 用完了就扔掉，从不写回中央仓库。

等一下——softmax 的分母是全行的和，只看一小块怎么知道全局？这就是 FlashAttention 的第二个魔法：**在线记账**。

每行维护两页账：m（当前见过的最大分数）、l（当前 exp 之和），再随身携带一笔 O 的累加。新货箱到来时：

```
m ← max(m_old, m_block)
l ← l_old · e^(m_old − m) + Σ_j e^(s_j − m)
O ← O_old · e^(m_old − m) + Σ_j p_j · V_j ,  其中 p_j = e^(s_j − m)
```

听起来像作弊？其实只是"汇率换算"：新的最大值 m 变大了，旧账本里的每一笔 exp 都要按 e^(m_old − m) 这个汇率打折，然后再并入新账。最后 O/l 就是精确的 softmax 加权平均。

这套仓库调度能省多少？给一组精确数据锚点：N=8192、d=128、fp16。标准流程 S/P 六进六出中央仓库，约 12N² ≈ 805MB；分块（B_r=B_c=128）后 K/V 货箱重复搬运约 4N²d/B_r ≈ 270MB，减少约 3 倍。论文报告 FlashAttention 让注意力计算快 2–4 倍（随序列长度变化）、GPT-2 端到端训练快约 15%；FlashAttention-2 又在其上提速约 2 倍，在 A100 上摸到理论峰值的约 73%。

那么问题来了：这套"打折记账"凭什么和一次性算完精确等价？下一节用公式验一验。

## 六、理论验证：roofline 与账本数学

### 6.1 roofline：先分清你在哪一侧

任何算子的耗时都满足：

```
T ≥ max(F / P_peak, B / b_bandwidth)
```

其中计算强度 I = F/B（FLOP/byte）就是"每搬一个字节能干多少活"：

- 大 GEMM（N=4096 方阵，fp16）：I ≈ N/3 ≈ 1365 FLOP/byte，远超 156 → **算力侧**，请重型叉车（Tensor Core）。
- 注意力矩阵乘（d=128，fp16）：I ≈ d = 128 FLOP/byte，低于 156 → **带宽侧**，再快的叉车也在等仓库。
- 解码时单 token 的"矩阵乘"退化成一行的 GEMV：I ≈ 1 → 彻底的带宽侧。

### 6.2 把仓库的流量账摆出来

- 标准实现：S/P 六趟进出，加 Q/K/V 读、O 写 → T_std ≈ 6N² + 4Nd（元素次）。
- 分块实现：Q 读一次、K/V 货箱随外层循环重复搬运 → T_tiled ≈ 2Nd + 2N²d/B_r。

代入 N=8192、d=128、B_r=128：805MB 对 270MB，恰好 3.0 倍——上一节的直觉和账本完全对得上。

### 6.3 在线 softmax 的归纳证明

命题：处理完前 i 个块后，O_i / l_i 等于只看这 i 块时的精确 softmax 加权和。

证明只需要一步：旧项分子 e^(s_j − m_old) 乘上汇率 e^(m_old − m_new) 后等于 e^(s_j − m_new)，即旧账在新标尺下的准确价值；分母 l 用同一个汇率重标定后与新块相加，再除以 l 即得标准 softmax。数学归纳成立，浮点上没有任何近似，只是求和的结合顺序变了。

说白了：账没记错，只是把"每次来新货都全盘重算"换成了"按汇率折算"。你可能立刻冒出几个问题，我们一个个回答。

## 七、性质补证：你此刻正在想的四个问题

**Q1：为什么不干脆把 K、V 全搬上工作台？**
装不下。N=8192、d=128，一个头的 K 就是 2MB；工作台只有约 200KB，差一个数量级。长序列 N=32K 时一个头的 K 要 8MB——想都别想。分批从中央仓库搬运不是可选项，是唯一出路。

**Q2：分块会不会引入近似误差？**
不会。这不是"近似注意力"，是精确注意力换了个记账顺序。数学上严格等价，浮点差异只来自加法结合顺序，量级与标准实现相当；FlashAttention 论文也验证了训练收敛一致。

**Q3：bank conflict 是个什么东西？**
工作台只有 32 个抽屉（bank），warp 的 32 个人同时取货。如果 32 人都去抓同一个抽屉，就要排 32 次队。生产代码里把 K/V 货箱每行按 D+1 的步长摆放，抽屉永远错开——细节见下一节的 padding。

**Q4：分块后不就省流量了吗，为什么还要 FlashAttention-2？**
因为分块后的计算强度约等于块宽 B_r（≈128），还在盈亏线附近徘徊；而且小 batch 时并行度不足、非矩阵乘开销占比高。FA-2 把外层循环从"按 K 分块"改成"按 Q 分块"提高并行，削减非矩阵乘运算，把工作台用得更满。一句话：账记对了，但车间还不够忙。

这些细节，直接看代码最清楚。

## 八、代码落地：一个跑得通的教学版 FlashAttention

下面是一个约 280 行的完整 CUDA 程序：纯 fp32、无 Tensor Core，但完整实现了分块、在线 softmax、causal 掩码和 bank conflict 规避，并与 CPU 精确对照。编译运行：

```bash
nvcc -O3 -arch=native mini_fa.cu -o mini_fa
./mini_fa
```

代码与仓库比喻的映射，读之前先记好：

- `sK`/`sV`：搬进工作台的 K/V 货箱（共享内存），每行 65 列，多出的 1 列 padding 用来错开 32 个抽屉（bank）。
- `q`、`o`、`m`、`l`：装在工人口袋（寄存器）里，O 只在最后一刻写回中央仓库。
- `__shfl_sync`：口袋里某个工友的值，喊一嗓子广播给整个班组。
- `__launch_bounds__`：按住寄存器预算，保证 1024 人的班组能顺利开工（实测 32 个寄存器、0 spill）。
- 每 block 处理 B_r=64 个 query 行，逐批吃掉 K/V 货箱；生产级 FA 用 128，教学版为可读性折中。

在 GTX 1050 上（N=512、D=64、causal=1）的实测输出：

```
mini-FlashAttention (N=512, D=64, causal=1)
  max abs error vs CPU ref : 2.145767e-06
  avg kernel time          : 0.965 ms
  HBM element traffic      : 1703936 (naive) vs 589824 (tiled), 2.9x less
PASS
```

教学版离生产还差不少：没有 Tensor Core 的 `mma` 指令、没有 fp16/bf16、没有 128×128 的甜点块、causal 也只做了朴素的整块跳过。这些差距，正好引出下一节的工程挑战。

## 九、工程挑战：极端场景与进阶武器

先把两个极端场景摆上桌：

**场景一：序列 128K。** S = 128K² × 2B ≈ 34GB，一个头就要这么大——不 tiling，货堆能把仓库直接淹了。此时分块不是优化，是能不能跑的问题；causal 下还有一半三角区可以整块跳过，调度得好等于仓库流量再砍半。

**场景二：解码 batch=1。** 每步只有一行 query，GEMM 退化成 GEMV，计算强度约等于 1。每次开工都要把模型权重和 KV cache 整个过一遍中央仓库，算力在旁边闲得发慌。这时候的优化目标是"少搬、搬小的"：

- **KV cache 分页（PagedAttention）**：给 KV cache 装上类似操作系统虚拟内存的页表，让仓库货架可以不连续，消除碎片、按需扩容；vLLM 论文报告吞吐提升 2–4 倍。
- **GQA/MQA**：让多个头共享同一套 KV 货架，仓库库存直接砍掉数倍。
- **量化（FP8/INT4）**：货箱体积砍半甚至砍到 1/4，同一条公路一趟多拉几倍的货。

算力侧也没躺平。FlashAttention-2 在 A100 上达到约 73% 理论峰值；FlashAttention-3 在 H100 上报告 740 TFLOPS（约 75% 峰值）、比 FA-2 再快 1.5–2 倍。Hopper 的 TMA 像一条自动传送带，搬运工不用干等，异步把下一批货箱送到工作台；warp specialization 干脆把班组拆成搬运班和装配班；软件流水让"上一批在加工、下一批在路上"。

**评论区预埋**：

- "块大小 128×128 是不是拍脑袋定的？" 不是。太小，每趟搬运的货少、搬运次数多；太大，工作台和口袋不够用、可并行块数减少、收尾时大批工人闲着（tail effect）。FA 论文扫过块大小，128 是容量、并行度和搬运次数之间的甜点。
- "标准 attention 用 cuBLAS 也能跑出不低的 FLOPS，为什么还说它慢？" FLOPS 利用率高不等于时间短。带宽侧的活，叉车再猛，货没到就是空转。判断要看 Nsight Compute 里的 DRAM 吞吐和 SM 忙闲，而不是只看 FLOPS。

工具就一句话：Nsight Compute 打开，看 DRAM throughput、SM 利用率、bank conflict，哪个红灯亮就先治哪个。

这套仓库调度学，能走多远？最后一节看它如何溢出 attention。

## 十、跨域拓展与总结

同一套"就地加工、用完即弃、在线记账"的仓库调度学，已经走出了 attention：

- **Flash Decoding**：长序列解码时把 K/V 货箱分给多个车间各自算局部 softmax，最后用同样的"账本合并"归并——在线 softmax 思想的直接复用。
- **Mamba/SSM 的 chunked scan**：状态空间模型的分块扫描，同款"分块 + 状态修正"打法。
- **稀疏/滑动窗口注意力**：按 mask 直接跳过整箱货，仓库少搬，速度自然上来。
- **生态落地**：PyTorch 的 `scaled_dot_product_attention`、xformers、vLLM、FlashInfer 已经把它变成开箱即用的基础设施。

最后，把这篇文章浓缩成 10 条：

1. 动手前先算计算强度，分清算力侧还是带宽侧（A100 分界线：156 FLOP/byte）。
2. 中央仓库的带宽，是 Transformer 最容易被忽视的天花板。
3. 分块 tiling 是万能钥匙：中间货品就地加工、用完即弃。
4. online softmax 记账法：旧账打折 + 新账入账，数学精确、不是近似。
5. 工作台与口袋要物尽其用；bank conflict 用 padding 错开抽屉。
6. 大 GEMM 交给 Tensor Core/cuBLAS；小算子能融合就融合，少跑仓库。
7. 解码是带宽侧：KV cache 分页、GQA/MQA、量化，少搬、搬小的。
8. 长序列必须 tiling；FA-2/FA-3 与 TMA、warp specialization 是下一代武器。
9. 一切优化以 Nsight Compute 实测为准，FLOPS 利用率会骗人。
10. 把"算"的思维换成"搬"的思维，Transformer 算子加速就真正入门了。
